# Azure Managed Redis exposure source proof (2026-10-28)

Microsoft identifies `Microsoft.Cache/redisEnterprise` as both Redis Enterprise and Azure Managed Redis. A database child is required for a functioning instance: [ARM resource reference](https://learn.microsoft.com/en-us/azure/templates/microsoft.cache/redisenterprise).

The parent LIST and one resource-bound GET use `2026-10-01-preview`, the first [Redis Enterprise API version with cluster `firewallRules`](https://learn.microsoft.com/en-us/azure/templates/microsoft.cache/change-log/redisenterprise). Its [resource schema](https://learn.microsoft.com/en-us/azure/templates/microsoft.cache/2026-10-01-preview/redisenterprise) exposes `properties.publicNetworkAccess`, `properties.hostName`, and each firewall rule's `sourceAddressPrefix`. The bounded, paged read-only child operation remains [Databases - List By Cluster](https://learn.microsoft.com/en-us/rest/api/redis/redisenterprisecache/databases/list-by-cluster?view=rest-redis-redisenterprisecache-2025-07-01), `GET {clusterId}/databases?api-version=2025-07-01`; it exposes each database's client TCP `port` and `clientProtocol`.

The collector validates parent-bound child IDs and preserves incomplete/denied status. The parent GET prevents a LIST projection from silently omitting the firewall. Native analysis joins the explicit public gate, firewall sources, and observed database ports: empty firewall rules admit public sources, a valid public IPv4 or IPv6 prefix proves a declared listener, and private-only prefixes block direct public ingress. Missing or malformed rules without a positive public prefix remain unresolved, as do unsupported/denied preview reads. A disabled gate blocks regardless of the firewall. [Azure Managed Redis connectivity guidance](https://learn.microsoft.com/en-us/azure/redis/troubleshoot-connectivity) confirms that configured firewall rules require the client IP to be included. The analysis does not claim authentication or successful connection.
