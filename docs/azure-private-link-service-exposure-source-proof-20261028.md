# Azure Private Link Service sharing source proof

[Private Link Service overview](https://learn.microsoft.com/en-us/azure/private-link/private-link-service-overview) documents three provider visibility modes, the auto-approval subscription list, and provider-side private endpoint connection approvals. An approved connection can send traffic; a pending request cannot. Automatic approval is an access grant for future connections. The private service alias permits requests from anyone with the alias when visibility is unrestricted, but manual approval is still required.

[Private Link Services GET](https://learn.microsoft.com/en-us/rest/api/virtualnetwork/private-link-services/get?view=rest-virtualnetwork-2025-05-01) returns `accessMode`, `visibility.subscriptions`, `autoApproval.subscriptions`, and `privateEndpointConnections` under one provider resource. [The API change log](https://learn.microsoft.com/en-us/azure/templates/microsoft.network/change-log/privatelinkservices) records that `accessMode` was added in 2025-01-01; the collector now uses 2025-05-01 and a single read-only full GET per listed service, through the existing per-scan request cache. It retains only access mode, subscription IDs, endpoint IDs, connection status, and state; the alias and connection descriptions are discarded.

The native assessment reports a cross-subscription grant when another subscription is on the auto-approval list or has an approved private endpoint. It treats alias-wide visibility and a foreign subscription that can only request approval as unresolved potential access. It reports no external grant only when access is restricted to the owner subscription and no external approvals exist. This is private cross-subscription reachability, not public internet reachability or proof that the consumer can authenticate to the application.

Focused fake-transport tests cover the cached full GET, safe projection, approved, pending, same-subscription, auto-approved and unrestricted cases. No Azure write operation is used.
