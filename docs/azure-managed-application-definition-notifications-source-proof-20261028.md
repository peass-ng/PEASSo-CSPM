# Managed Application definition notification source proof

- [Application Definitions List By Resource Group](https://learn.microsoft.com/en-us/rest/api/managedapplications/application-definitions/list-by-resource-group?view=rest-managedapplications-2019-07-01) is a read-only ARM GET. The response includes definition `isEnabled`, `managementPolicy.mode`, `authorizations`, and `notificationPolicy.notificationEndpoints[].uri`. Package and artifact URIs and inline templates may contain secrets; the collector retains none of them. It reduces notification URIs to hostnames, discarding paths and queries.
- [Managed Applications with notifications](https://learn.microsoft.com/en-us/azure/azure-resource-manager/managed-applications/publish-notifications) documents that a definition's webhook receives lifecycle POSTs for instances referencing it. Notifications carry the application ID, definition ID, event type, time, provisioning state, and sometimes error details. The documentation explicitly shows a query parameter as a webhook authentication secret, so a snapshot must not retain the URI.
- [Applications List By Subscription](https://learn.microsoft.com/en-us/rest/api/managedapplications/applications/list-by-subscription?view=rest-managedapplications-2019-07-01) returns `applicationDefinitionId`. The existing application inventory now retains that ID to join instances to definitions without collecting parameters or outputs.
- `peaso.analysis.internet_exposure._azure_managed_application_definition` reports a configured webhook outside verified tenant domains only for an enabled definition with an observed active instance. Missing instance/domain inventory or disabled definitions remain UNKNOWN. The detector does not claim that every non-verified domain is independently proven third-party owned or that a webhook has actually received a POST.
