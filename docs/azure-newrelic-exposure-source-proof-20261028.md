# Azure Native New Relic telemetry exposure source proof

The [monitor LIST](https://learn.microsoft.com/en-us/rest/api/newrelic/monitors/list-by-subscription?view=rest-newrelic-2026-06-01) returns monitor identity, provisioning state, monitoring status, marketplace subscription status and New Relic account and organization identifiers. The collector uses the selected-subscription LIST with bounded same-path pagination and retains only those safe fields. It discards the account ingestion key, SSO details, user metadata and arbitrary properties.

The [monitored-resources operation](https://learn.microsoft.com/en-us/rest/api/newrelic/monitors/list-monitored-resources?view=rest-newrelic-2026-06-01) is a documented read-only POST with an empty body. It returns each Azure resource ID plus explicit `sendingLogs` and `sendingMetrics` states. The collector permits only the exact ARM operation, checks pagination stays on the same monitor route and retains just the resource ID and send states. A successful, enabled monitor with an active marketplace subscription and an enabled send state produces a native third-party telemetry finding; absent or ambiguous states remain UNKNOWN.

The [Azure Native New Relic overview](https://learn.microsoft.com/en-us/azure/partner-solutions/new-relic/overview) identifies the separate New Relic account. [New Relic's account-access documentation](https://docs.newrelic.com/docs/accounts/accounts-billing/account-structure/new-relic-account-structure/) explains that New Relic groups, roles and account grants control access, including for outside contractors. Those downstream New Relic grants are not returned by Azure ARM's monitor or monitored-resource APIs. Likewise, manually installed agents may report independently of the ARM integration. Full onward access and agent-only telemetry therefore remain outside a read-only Azure management scan.
