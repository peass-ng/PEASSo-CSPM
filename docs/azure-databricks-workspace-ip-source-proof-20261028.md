# Azure Databricks workspace IP access read

The Azure collector accepts `auth.databricks_workspace_token_secret`, a mapping from an exact ARM workspace resource ID to a pre-existing workspace PAT. Hosted connector intake uses the collector's bounded ID/token validator before accepting this structured auth field. The connector encrypts the map at rest and redacts it from responses and logs. Scan resume compares the sorted workspace IDs while permitting PAT rotation for those same IDs; token values are never included in the comparison. The collector binds the ARM `workspaceId` to the `adb-{id}.{number}.azuredatabricks.net` host before any request. No account or ARM service-principal token is exchanged for a workspace token. Missing credentials and mismatches produce no workspace request.

The only native requests are GET `/api/2.0/workspace-conf?keys=enableIpAccessLists` and, when enabled, GET `/api/2.0/ip-access-lists`. The transport disables proxies and redirects, caps the response, rejects duplicate JSON fields, and projects only status, list type, enabled state, and IPv4 ranges. The [workspace IP list API](https://docs.databricks.com/api/networking/v1/ip-access-list) documents the complete list GET and its response shape. [Workspace configuration guidance](https://learn.microsoft.com/en-us/azure/databricks/security/network/front-end/ip-access-list-workspace) documents the feature flag and ALLOW/BLOCK semantics.

The analyzer proves a blocked direct public path when an enabled BLOCK list covers `0.0.0.0/0` or all active ALLOW ranges lie within RFC1918 space. Otherwise it joins the separately collected account context ingress policy and preserves `UNKNOWN` if that policy is unavailable or cannot resolve the path. [Databricks documents](https://learn.microsoft.com/en-us/azure/databricks/security/network/front-end/ip-access-list) that context-based ingress is evaluated jointly with workspace IP access lists. Policy changes can also take a few minutes to become effective.
