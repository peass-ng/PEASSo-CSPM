# Azure Databricks workspace IP access read

The direct Azure collector accepts `auth.databricks_workspace_token_secret`, a mapping from an exact ARM workspace resource ID to a pre-existing workspace PAT. It validates the token shape and binds the ARM `workspaceId` to the `adb-{id}.{number}.azuredatabricks.net` host before any request. No account or ARM service-principal token is exchanged for a workspace token. Missing credentials and mismatches produce no workspace request.

The only native requests are GET `/api/2.0/workspace-conf?keys=enableIpAccessLists` and, when enabled, GET `/api/2.0/ip-access-lists`. The transport disables proxies and redirects, caps the response, rejects duplicate JSON fields, and projects only status, list type, enabled state, and IPv4 ranges. The [workspace IP list API](https://docs.databricks.com/api/networking/v1/ip-access-list) documents the complete list GET and its response shape. [Workspace configuration guidance](https://learn.microsoft.com/en-us/azure/databricks/security/network/front-end/ip-access-list-workspace) documents the feature flag and ALLOW/BLOCK semantics.

The analyzer proves a blocked direct public path when an enabled BLOCK list covers `0.0.0.0/0` or all active ALLOW ranges lie within RFC1918 space. Otherwise it preserves `UNKNOWN`: [Databricks documents](https://learn.microsoft.com/en-us/azure/databricks/security/network/front-end/ip-access-list) that account context-based ingress is evaluated jointly with workspace IP access lists. Policy changes can also take a few minutes to become effective. Hosted connector intake does not yet accept the new mapping; its validator has an exact reviewed-source transition and needs a separate reviewed update.
