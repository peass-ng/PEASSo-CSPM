# AWS ECS selected-content timing boundary (2026-10-28)

The saved bf67 scan recorded 9,752 `DescribeTaskDefinition` calls and 838.8 additive SDK seconds. Its snapshot has 4,755 native task definitions (4,754 in one scope) and 4,778 automatic selected-configuration items (4,771 in that same scope). This matches two distinct reads for nearly every task definition. The content read uses a separate hardened client, source-bound request approval, exact native response provenance, private detector capture, and a safe projection that discards raw values before caching. The native response is already collected when automatic source discovery starts. Reusing the ordinary native cache for selected content would bypass that privacy and provenance boundary; increasing the one-worker per-scope pool would not help the dominant single scope.

The remaining question is how much of the scan tail belongs to automatic selected content rather than ECR image content and public checkpoints. `collection.automatic_content_scope` now measures each automatic scope from start through its settled result, recording only stage duration and CPU in the existing bounded runtime metrics. No scope, source, account, secret, or raw response is added to metrics. The next guarded scan can compare its duration with `collection.job`, `secret.trufflehog.prepared_process`, and `worker.public_checkpoint` before changing detector consumer concurrency.

This is instrumentation, not a claimed speedup. The local machine has neither Kingfisher nor TruffleHog available, so a synthetic consumer throughput measurement would not prove production behavior. `python3 -m py_compile peaso/collectors/aws.py` and two focused ECS/coverage tests passed. The broader ECS two-phase file had 41 passes and six failures in tests expecting Linux volatile `/dev/shm` batching on this macOS host; the selected configuration source was not changed. No cloud write, push, deploy, or production scan was performed.
