# GCP Service Usage late-page quota recovery, 2026-10-29

The same-scope production GCP scans 66da190d and 52588fc3 used the same connector and request. The former collected 12,968 Service Usage items in 65 successful page requests. The latter collected 12,600 in 63 successful pages, then received HTTP 429 on five attempts for the next page and ended `partial`. Under stable inventory, one 200-item page and a final 168-item page remained; the saved source request intentionally omits the page cursor. The request recorded no `Retry-After` header or per-attempt waits, so its provider pacing cannot be reconstructed.

This candidate extends **only** `GET https://serviceusage.googleapis.com/v1/projects/{project}/services` with a valid 1–200 `pageSize` by at most two extra retries for HTTP 429. It applies only when the connector did not set `retries` explicitly. Other 429 routes, other HTTP errors, network exceptions and explicit retry settings retain the original limit. Existing per-attempt `Retry-After` handling, the 60-second single-wait cap, call limit, cancellation and scan deadline still apply. The two extra waits have a combined 90-second cap; persistent quota leaves the collection incomplete with an explicit error.

An offline fake-session pagination test returned the same 568 ordered, unique items after five 429 responses and one successful extra attempt; 8 physical HTTP calls covered three pages, with 15.5 seconds of fake-clock backoff and no additional calls on all-200 pages. Persistent 429 stopped after 7 attempts on its page, 31.5 seconds of fake-clock backoff, and retained the first complete page. A 60-second `Retry-After` sequence hit the extra-wait budget before a seventh request. Explicit retries and a non-Service-Usage route retained 5 attempts; a short scan deadline stopped before the extra retry. The focused source and existing Retry-After suite passed 18/18 with no provider calls.

This is a bounded recovery candidate, **not** a production coverage or timing win. A quota event can add at most two HTTP attempts and 90 seconds of extra wait for one page. The exact 52588 result cannot be repaired retroactively; a future same-scope scan must prove collected status and item coverage. No cloud scan, provider mutation, model call or IAM Access Analyzer call was made for this receipt.
