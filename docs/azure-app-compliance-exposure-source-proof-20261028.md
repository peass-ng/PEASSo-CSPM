# Azure App Compliance Automation exposure source proof

The [2024-06-27 report LIST](https://learn.microsoft.com/en-us/rest/api/appcompliance/report/list?view=rest-appcompliance-2024-06-27) is tenant-scoped and paged. Its response carries the report's source `subscriptions` and optional `storageInfo.subscriptionId`. The collector projects only these ownership facts and report state; report contents, compliance evidence, storage account names, and offer details are excluded. A storage destination outside all reported source subscriptions is a cross-subscription data delivery path. Missing source or destination identity is unresolved.

The [2024-06-27 webhook LIST](https://learn.microsoft.com/en-us/rest/api/appcompliance/webhook/list?view=rest-appcompliance-2024-06-27) is paged per report and supplies `status`, `provisioningState`, `events`, `sendAllEvents`, and `payloadUrl`. Its schema also includes `webhookKey`. The collector retains only the URL scheme and hostname, never the path, query, user information, or key. An enabled, succeeded webhook with a subscribed event is a configured report notification to its receiver. Disabled webhooks and enabled webhooks with no selected events cannot deliver report events. Partial child inventory leaves the report unresolved unless a cross-subscription storage destination is already proven.

The [webhook GET schema](https://learn.microsoft.com/en-us/rest/api/appcompliance/webhook/get?view=rest-appcompliance-2024-06-27) defines the event/status fields and confirms that the key is a secret. No mutating API is used. Both LIST operations pass through the scan's request cache and bounded pagination; each report's webhook list is read once.

This is configuration evidence, not proof that a webhook receiver is owned by a separate organization or that delivery succeeded. The assessment records only the receiver hostname and the API's delivery status. Manually downloaded report copies and downstream sharing after download are not enumerable from these read-only management APIs.
