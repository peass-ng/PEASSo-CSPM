# Microsoft Entra cross-tenant access policy source proof

- [Default cross-tenant access settings](https://learn.microsoft.com/en-us/graph/api/resources/crosstenantaccesspolicyconfigurationdefault?view=graph-rest-1.0) and [partner settings](https://learn.microsoft.com/en-us/graph/api/crosstenantaccesspolicy-list-partners?view=graph-rest-1.0) are read with one Graph GET each per tenant. Partner settings inherit null fields from the default. The partner LIST expands identity synchronization, retaining only `isSyncAllowed`, inbound B2B target/access types, inbound security-claim trust booleans, and partner tenant IDs.
- The [cross-tenant policy overview](https://learn.microsoft.com/en-us/graph/api/resources/crosstenantaccesspolicy-overview?view=graph-rest-1.0) says service-default B2B collaboration inbound is allowed and direct connect inbound is disabled. [Inbound trust](https://learn.microsoft.com/en-us/graph/api/resources/crosstenantaccesspolicyinboundtrust) accepts external MFA/compliant-device/hybrid-join claims. [Inbound user synchronization](https://learn.microsoft.com/en-us/graph/api/resources/crosstenantusersyncinbound?view=graph-rest-1.0) allows partner-created user objects. Native analysis reports partner sync or external claim trust with an enabled inbound B2B path as configured cross-tenant identity trust. B2B allowance alone stays UNKNOWN because it does not grant a specific application or resource.
- The policy does not identify the application-managed audience for every External ID application. [Microsoft identity authorization guidance](https://learn.microsoft.com/en-gb/entra/identity-platform/authorization-basics) explains that authorization logic is often implemented inside the application or a dedicated authorization service. Graph policy and app-registration reads cannot establish that external authorization state or all users who can access application data. This is the remaining complete-exposure API limit for Microsoft Entra External ID.
